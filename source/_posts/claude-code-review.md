## 一句话总结

Claude 写了 Claude Code 约 90% 的代码。Anthropic 没取消 code review，而是**把大部分"读代码"的活交给机器，把人的时间留给只有人能判断的事**，再配上一层快速回滚兜底。6→9 月，合并的 PR 翻倍多，而需要 revert 的比例反而降了 40% 以上。

## 先看几组数据

| 指标 | 数字 |
| --- | --- |
| Claude 写的代码占比 | ~90% |
| Anthropic monorepo 每天落地改动 | 5 月 ~2500 → 9 月 30000+ |
| 研究预览期内部 PR 拿到实质评论的比例 | 16% → 54% |
| 合并 PR | 6→9 月翻倍多 |
| revert 比例 | 同期下降 40%+ |
| 一个 CLI PR 极端情况 | 一夜跑了 50+ 轮审查 |

## 核心思路：换个问题

文章里有句话很关键：

> "有没有人读过代码？"是个不精确的代理指标。真正该问的是：**这个改动可能出什么问题，哪个检查（自动还是人工）最该抓住它？**

所以审查的时机也变了——以前是"写完 → 开 PR → 等同事"这种**终点的一道门**；现在是**像拼写检查一样持续运行**：大多数改动在人来之前已经被 Claude 审过、修过一遍。

还有个常被忽略的成本结构：**人的时间花在"审"和"修坏的代码"两头**。只砍第一头，第二头涨上来等于没省。所以他们把 revert 率和事故率当成**护栏指标**：这两个涨了，就说明时间只是被挪走了，没省下来。

## 七层流水线

### 1. PR 之前就自验证

大多数审查发生在 PR 存在之前。给 Claude 一个能**跑**的东西（测试、构建、跟设计稿对比的截图），要求它**展示输出**，而不是说"我完成了"。然后让子 agent 用**全新上下文**再审一遍 diff。

Boris Cherny（Claude Code 作者）的说法：**让模型能验证自己的工作，大概是最重要的一件事**，能让结果好 2–3 倍。

同一个问题被反复 flag 时，修**源头**而不是修这一处：改 skill、加 lint 规则、或更新两文件：

- `CLAUDE.md`：项目是什么——技术栈、约定、目标与非目标。每次审查都会加载，所以要**短**，细节指到别的文档。
- `REVIEW.md`：由代码 owner 写，告诉 reviewer 这块地什么最重要。好的 REVIEW.md 很简短：说清这个 repo 里**失败长什么样**（文档 repo = "它说谎"，配置 repo = "它路由错"）、限制 nit 数量、列出跳过的路径、要求给**文件 + 行号**当证据而不是靠文件名猜。

### 2. 每个 PR 都跑 AI 审查

每个 PR 在人来之前先过 Claude：对着整个 repo 和 PR 声明的意图读 diff，问"它解决了自己的问题吗？契合系统吗？会不会弄坏别的？"。修 bug 的 PR 还要找**根因**。

发现由**另一批 agent 验证**：几组同时找 bug → 另一组投票 → 票数够才发评论。只涉及风格/诊断/清理的直接丢。这套过滤还做过 A/B 测试。剩下的按严重度排，每条标 `Important` / `Nit` / `Pre-existing`——**PR 没引入的老问题不该算在作者头上**。

每条发现都必须回应：要么修，要么带理由 resolve。

### 3. 安全审查能卡合并

安全单独一条自动审查。**bug 审查或安全审查只要还有未关闭的 finding，就禁止合并**。要么修，要么写个短理由关掉（这是清 false positive 的方式）。后续 commit 修好了，finding 自动消失。

### 4. 自动检查能卡合并

常规那套：lint、类型检查、各平台测试、构建。一个典型 CLI PR 可能在有人看之前就跑了几十个检查。PR 模板要填"怎么测的、怎么撤销"，Claude 可以代填，但**发起变更的人要签字**。

### 5. 人工批准按风险分级

这是我觉得最值得抄的设计：

| 风险 | 例子 | 需要几个真人批准 |
| --- | --- | --- |
| 低 | 文档、文案、纯内部功能、带 flag 的增量变更 | 自动审查 + 安全检查绿了就 **0 人** |
| 中 | 普通产品改动；缓存、自动更新、系统提示等敏感区 | **1 人** |
| 高 | 最高风险代码 + 一小组永远要两人的路径 | **2 人** |

几个细节很讲究：

- **分级由变更决定，不由作者决定**。分类器读改动定档，第二个分类器判断"即使档位说不用人，这次是不是还得加人"。
- **只有可信作者**（repo 信任名单，基本是团队自己）能走轻路径；其他人一律要第二个人批。
- **agent 的批准永远不算真人**。自动审查能放行低风险改动，但填不了"必须是人"的坑。
- **谁发起谁负责**：agent 写的 PR，指挥 agent 的人就算必需 reviewer 之一——跟亲手敲代码一样。
- **批准只覆盖某个 commit**。新 commit（agent 推的、手工解冲突的）来了，得重新批。

### 6. merge queue + flag + 灰度

merge queue 会把改动应用到 main 上**重跑所有检查**，防止两个单独能过的 PR 合并后把 main 搞坏。新行为先对 Anthropic 员工上 flag（内部重度使用往往先于用户暴露回归），公开发布先走 `latest` 再走 `stable`。

### 7. 快速发现、快速回滚

总会有漏网的。最后一层拼的是**发现和回滚的速度**：flag 不用部署就能关；有每周 on-call 轮值；事故复盘会追问"哪一层本该抓住它"。

有个同事说得很实在：**放慢当然能降错误率，但那主要是因为你啥都做得少了**。他们宁可练"更快发现和修复"。

## reviewer 自己怎么越用越好

这是全文最有意思的部分——**把事故变成 eval**：

- 收集历史上导致事故的 PR（连同 fix-forward 和 revert），让懂那块代码的工程师确认每个 bug 在哪。
- reviewer 每天跑这个集合，**每次改动都拿全集打分**。
- 测**噪声**：按人对评论的反应分类（改了 / 说它错了 / 是有意的 / 不重要）；还会在已知干净的 PR 上跑，数它误报了多少。

他们还发现一个反直觉的点：**噪声对 agent 作者代价更大**。人看到 nit 一秒就过了；agent 会去修 → 多一个 commit → 多一轮审查。所以：

> **审查必须收敛。** 一个 agent 作者和一个 agent reviewer 可以把彼此无限忙下去——真有 PR 一夜跑了 50 多轮。

对反复被 flag 的东西做 `git blame`，发现约 **59% 是 reviewer 第一遍就存在的老代码**——它不是每轮找到新 bug，而是每轮多找几个老的。于是改了重新审查策略：

- **轮次上限**：3 轮后让作者退后重新考虑方案；
- 头几轮之后**只审 diff**；
- 标记 bug 的**类别**，让作者一次修完所有实例，而不是一行；
- **不重复**已发过的 finding。

另外还有 agent 每晚对存量代码跑，提前抓老 bug。

## 人还留在哪些环节

把资深工程师从深度工作里拽出来接一个例行错误，代价远高于自动审查。团队明确保留了人的责任：

- **决定要不要做**：方向、品味、范围；
- 审**高风险代码**：计费、自动更新、CI 工作流；
- 审**会被别人复制的架构**；
- **读证据**：测试输出、跑了什么命令返回了什么、截图、reviewer 的发现。说不清"这些检查会漏什么"时，就该要求一次真审查，而不是快速点个通过；
- **对结果负责**：每个上线的变更都得有人担责，不管是谁敲的。

至于"机器读代码了，人还怎么学代码"这个第二职责，他们没有正式流程：想懂某块就让 Claude 写针对那片的解释，几分钟的事；有人干脆让 Claude 生成一个可视化那块代码的 artifact。

## 对我们做项目的启示

看完最大的感受是：**它不是"用 AI 替掉 review"，而是把 review 拆成"机器擅长的"和"人擅长的"两类，再用风险分级决定哪类走哪条路。**

能直接借走的东西：

1. **让 agent 先自证**：给它能跑的命令，要求贴输出，而不是说"done"。
2. **审查前置**：PR 之前先自审一遍（找 bug / 简化 diff / 端到端验证），人来的时候看的是"证据"不是"初稿"。
3. **风险分级**：文档类 0 人、普通改动 1 人、敏感/架构 2 人，别对所有 PR 用同一把尺子。
4. **谁发起谁负责**：agent 写的代码，发起人照样是 reviewer，跑不掉。
5. **护栏指标**：只盯"审查时间"会被骗，要同时盯 revert / 事故率。
6. **review 要收敛**：给轮次上限、只审 diff、按类别修，别让 agent 和 agent 互相喂。
