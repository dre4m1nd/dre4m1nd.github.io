## 摘要

**Super Agent 是一个"持续存在"的 agent 实体：它不再被绑在"一次手动发起的会话"上，而是跨会话保留上下文，同时推进多个复杂任务且互不干扰。** 人负责定目标、看结果；系统负责调度和管 agent。

两篇文章几乎同时讲了这个东西——Agno 的 Ashpreet Bedi《Building a Super Agent》和 DeepSeek Harness 团队《Exploring Super-agent Design》。一个从产品角度描述它长什么样，一个从系统角度拆它怎么搭。这篇把两者合起来，讲清概念。

## 一、先看问题：为什么需要 Super Agent

过去一年，coding agent 和单任务 agent 已经证明模型能用工具解决复杂问题，人也越来越不用盯着。模型也变得更擅长协调多个 agent，跨会话组织调度工作变得可行。

但今天主流的设计撑不起"很多任务"或"整个团队"的用法：

**agent 仍然以"单个会话"为基本工作单位，会话之间互相隔离。** 一个用户并行跑多个任务时，只能手工在会话之间切换，还要记住每个会话里有什么。实际经验是：**一个人最多同时跟 3~5 个活跃会话。**

给现有 agent 加 CLI、MCP、外部连接器，能让它收到外部消息，但根本限制还在：
- 仍然是一个同步会话，长时间操作会阻塞
- 不同任务的上下文会混在一起
- 本地设备一离线，全停

> 在这样的设计下，**单个任务的上限是模型能力，多任务的上限是人的注意力。**

**解法**：把 agent 从"单个手动驱动的会话"里解耦，让它变成一个**连续实体**——跨会话保留上下文，同时推进多个复杂任务，任务之间不互相干扰。这就是 Super Agent。

## 二、Super Agent 的四个特征

| 特征 | 含义 |
| --- | --- |
| **Continuous（连续）** | 在你已经工作的地方直接交互（IM、GitHub），始终感觉是同一个 agent，不用想"哪个会话里有哪条信息" |
| **Productive（高产）** | 响应快，并行完成多个复杂任务；上一条命令没跑完就能接新指令 |
| **Proactive（主动）** | 不等逐步指令，监控环境事件，该干就干，不该干就闭嘴 |
| **Persistent（持久在线）** | 永远在线，连真实工作环境，长跑中能从异常自动恢复 |

关键在于：**没有任何一个 ReAct 循环能同时给出这四个特征，它们必须来自模型外围的系统架构。**

这和计算机系统领域面临的约束高度相似（永远在线、并发响应事件、从故障恢复），所以很多经典设计思路可以搬过来用。

## 三、它怎么工作：从触发到交付

Super Agent 由一个**触发器**启动，可以是三种：
- **消息**：有人在 Slack / Telegram / WhatsApp 里问一句"能看看这个 issue 吗？"
- **事件**：GitHub issue 被开了、PR 收到 review、构建挂了
- **定时**：该出早报了、每周五审文档、每分钟检查待办

触发之后，它先判断"这需要做什么"，然后有几种典型反应：

1. **直接回答**——"文档更新到哪了？"查一下给状态
2. **跑现成 agent**——"准备这周客户报告"，把请求和上下文转给已有 agent（代码类通常是 Codex 或 Claude Code，各自在沙箱里跑）
3. **组织更大的活**——"把文档准备好发版"，创建一个 Project + 若干 Task（查示例、更新 API 引用、写迁移指南），进队列等 agent 执行
4. **现造一个 agent**——没有合适的，就用平台上的工具按需造一个，这个 agent 之后还能复用
5. **接着干进行中的**——"PR 看着不错，补个空响应测试"，把反馈接到原 Task 上，退回给正在干的 agent
6. **不动**——重试过了、是重复 issue、或已经有人在处理。**有时候什么都不做才是对的。**

**工作全程在后台跑，你继续跟它对话。** 需要你看结果或做决定时，它才回来找你。理想情况下，你能 continue、cancel、fork 或 steer 它管的那些 agent 会话。

## 四、核心架构：两层分工

Super Agent 的骨干是**两层结构**：

- **Router 层（路由）**：长期存在，接管所有人机交互、全局协调和记忆，是系统的全局顺序点、协调点、记忆体。**它自己绝不执行任务**——只跟人对话、派活，甚至可以不带 Bash 工具。
- **Worker 层（工人）**：上下文隔离，高并发地干活。每个 Worker 只收到它订阅的 Thread 的消息，所以一个任务的上下文不会漏进另一个。

为什么要分两层？因为这里有个硬取舍：

- 所有事件进一个会话 → 上下文最连续，但 ReAct 一次一步，吞吐低，不同任务的细节还会互相污染
- 每个事件开新会话 → 吞吐最高，但没有全局上下文，结果彼此脱节，多个会话分别回复用户也很乱

两层结构同时拿到**连续性**（Router 持有全局上下文）和**吞吐**（Worker 隔离并行）。

> 有了这个结构，系统接管了上下文管理和并发执行，用户几乎不用想"会话"，始终面对同一个 Super Agent。**会话应该成为系统的实现细节，而不是用户的心智负担。**

这和传统 Agent Team 的区别：Team Lead 通常要深入理解任务、拆子任务、频繁协调成员，推理负担重；Router 只派活、在高层跟踪任务间关系，不拆解单个任务，所以**用一个更轻的模型通常就能又快又好**。

## 五、几个关键机制

### 事件驱动：先过滤，再派发

工作以触发器形式到达（聊天消息、PR 评论、CI 结果、邮件）。**先过滤再派发**，这样 agent 才能主动而不需要有人每次都敲 prompt。过滤掉的（重复的、无价值的、别人已经在处理的）就不会消耗资源。

订阅是**多对多**的：一个 Worker 可以订阅多个 Thread，一个 Thread 也可以有多个订阅者。多个 Worker 订阅同一个 Thread 时，新事件广播给所有订阅者，它们自己协调冲突——不需要点对点通信。输出侧，Worker 仍只把关键结论汇报给 Router，由它统一回复用户、同步全局记忆。

### Inline & Spill：把上下文当缓存管理

事件持续不断地来，往上下文窗口里塞多少信息就成了设计问题：塞太多，窗口爆、注意力被稀释；塞太少，模型要反复调工具读上下文，执行步骤增多。

**浪费上下文窗口就是浪费模型的智能。**

解法是借编译器的两个操作：
- **Inline**：把马上要用的信息放进当前窗口，省掉额外工具调用
- **Spill**：超预算或很少用的放窗口外，只留引用/摘要，要用时再读

再配上**局部性**：先给 ID + 摘要 → 逐步 inline 邻近内容（前后 IM 消息、同一 code review 里的相邻评论）→ 超长的截断留指针。

把这套一致地用在系统里所有对象上，就得到 **Chain of Recall**：每个对象有唯一 ID，注入时带上相关对象的 ID，形成引用图，模型可以顺着引用一跳跳回忆上下文，想回忆多深就多深。

### Acting Ahead：投机执行

根据环境信号，**在还不知道结果会不会被用之前，就先在后台干起来**。用额外的后台算力换人的等待和介入。结果有用就交付，没用就丢弃。

比如可以配一条"静默复现并修复"策略：有人报 issue，agent 先在后台复现、找修复，确认了才说话，否则全程安静。

### 全双工：别让后台任务堵住对话

经典 ReAct 里，同步的 `run()` 工具调用会阻塞整个循环——工具没跑完，会话什么都回应不了。

改成异步的 `start()` / `stop()`：`start()` 立刻返回 "Started"，循环不等；工具在后台跑完，结果作为新事件送回会话；模型也能 `stop()` 掉跑太久的后台命令。

这样前台对话就和后台任务解耦了——耗时任务在后台跑，agent 照样能回应人。

### 多通道：按渠道定规矩

不同渠道的沟通方式不一样，agent 要调整详细程度和表达方式：
- **IM / 即时通讯**：像人类同事，只在需要决策或签字时打扰，只问直接的问题，给短结论。一条有效硬规则是**每条回复不超过 100 词**
- **GitHub / 邮件 / 文档**：给结构化的、信息密度高的输出——PR 里写全问题背景、改动说明、验证结果

冗长的推理过程和频繁的工具调用都留在 Worker 会话里，绝不直接进外部渠道；对外沟通统一由 Router 负责。

### 算存分离：别把自己绑在一台机器上

本地 agent 默认把三样东西绑在一台设备上：跑 Agent Loop 的**算力**、要持久化的**会话状态**、**执行环境**（代码仓库、本地工具链）。设备一睡一断，agent 就停。

两步解耦：
1. **算力与状态分离**：Agent Loop 跑在无状态弹性容器里，会话状态放数据库。容器可以扩缩、重启、替换，状态保证连续性——**设备睡了不影响 agent 持久在线**
2. **算力与执行环境分离**：不把环境搬上云，而是 Agent Loop 在云上、环境留在原地，每个端点装个轻量 daemon（不存状态，只执行命令、返回结果）。这支持 **BYOM（Bring Your Own Machine）**——把你自己的开发机接进云端 agent

真实工作环境里有未提交的改动、私有凭证、内网服务依赖、特定硬件工具链，全同步上云的代价很高。所以更好的做法是**移动"大脑"，保留"手"**。

### Watchdog：独立于主系统的控制环

持久在线光靠算存分离不够，还得能从异常里自动恢复。**一个持久在线的分布式系统，如果只靠内部逻辑，很难长期可靠——它需要一个独立于主系统的控制环。**

而且 agent 的异常很多**不是崩溃**：进程还在跑，但模型卡在无产出的循环里，或者偏离了目标。所以不能只用进程存活探针。

Watchdog 是一个由定时消息驱动的独立会话，负责：
- 处理基础设施故障（API 错误、状态恢复失败）
- 用模型判断每个 Worker 是不是在**实质性推进**、有没有偏离总目标
- 发现异常就修，暂时性外部故障就反复重试

因为 Watchdog 本身是个有全套工具的 agent 会话，维护者可以用自然语言问它"为什么失败"，也能在系统运行时让它改主系统的行为（加/删 prompt、调触发规则）。

## 六、人管什么

Super Agent 的目标是接管今天落在人身上的**规划和协调**：哪些活要干、起哪些会话、在会话之间拷上下文、检查有没有干完、再叫另一个 agent 来 review。

但人并没有退出，位置往上移了：
- **定目标、管结果**——你负责"做什么、做成什么样"，系统负责"怎么调度 agent"
- **高风险处签字**——哪些改动影响哪些用户、能不能安全上线
- **读证据**——测试输出、命令结果、截图；说不清"这些检查会漏什么"时，就要求一次真审查
- **对结果负责**——每个上线的东西都得有人担责

它**不会替代你的主 coding agent**。日常开发你还是用自己的工具；Super Agent 接的是"尾巴上那一堆活"：SDK 改了之后测受影响的示例并修好、复现群里报的 bug 并带回失败测试和修复、自动看客户反馈并提议项目。**结果你还是要 review，只是不用自己管每个会话和跟进了。**

## 七、落到自己的项目

不需要一上来就搭整套系统。最小可用的形状：

1. **一个不干活的 Router**：只接需求、派任务、记状态。哪怕就是一个 5 状态的转移函数 + 轮询循环。
2. **状态存起来，转移写成函数**：状态放 JSON 或数据库，转移写成"校验事件 + 更新状态"的纯函数。模型只能发事件请求，允不允许由代码判定。
3. **Worker 上下文隔离**：每个任务一个独立会话/沙箱，别让上下文互相污染。
4. **完成要有证据**：模型说"做完了"不算完成，要能跑出测试/截图/日志。
5. **能停下**：给关键能力加开关，出问题不用发版就能关。
6. **有独立检查**：别只查进程活没活，要查"有没有实质推进"。

## 重点总结

**一句话**：Super Agent 把 agent 从"单会话"里解耦出来，变成一个持续存在、跨会话保留上下文、并行推进多个任务的实体。人管结果，系统管 agent。

**为什么需要**：主流 agent 以会话为单位且互相隔离，一个人最多跟 3~5 个活跃会话——单任务的上限是模型能力，多任务的上限是人的注意力。

**四个特征缺一不可**：连续（同一个 agent，不用管哪个会话有哪条信息）、高产（并行推进、不等上一条跑完）、主动（监控事件、该干就干、不该干闭嘴）、持久（永远在线、能自愈）。它们必须来自模型外围的系统架构，单个 ReAct 循环给不了。

**架构的骨架是两层分工**：

- **Router 不干活**——只接人、派活、记全局。它一旦也执行任务，就成了瓶颈，还会污染全局上下文。
- **Worker 上下文隔离**——只收自己订阅的消息，任务之间不互相污染，才能高并发。
- 这样同时拿到了**连续性**和**吞吐**，而单靠一个会话必然二选一。

**四个关键机制**：

- **上下文当缓存管**：Inline 马上要用的、Spill 超长少用的，留 ID 走引用（Chain of Recall）。浪费上下文窗口就是浪费模型的智能。
- **投机执行**（Acting Ahead）：在不知道结果有没有用之前先在后台干，有用就交付、没用就丢。
- **全双工**：把同步 `run()` 换成异步 `start()`/`stop()`，后台任务不堵住对话。
- **算存分离 + BYOM**：算力在云上、状态在数据库、环境留在原地——设备睡了 agent 不停。

**两个最容易被忽略的点**：

- **持久化 ≠ 持久在线**。存状态只是第一步，还要独立 Watchdog 判断"有没有实质推进"（卡在无产出循环里不等于崩溃）。
- **主动性要有闸门**。"该不动时不动"和"该干时干"一样重要，否则 agent 就是个快速反复重开已解决问题的噪音源。

**人的位置往上移了**：定目标、高风险签字、读证据、对结果负责。Super Agent 接的是"尾巴上那堆活"，不是替代你的主 coding agent。

**落地先做最小版**：一个不干活的 Router + 状态存库、转移写成函数 + Worker 隔离 + 完成要有证据 + 关键能力能一键关。
