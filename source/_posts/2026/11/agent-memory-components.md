> Anthropic《The components of agent memory》（2026-11-06）摘要：agent 记忆是跨会话保留的可读知识；判断「什么值得记」比「怎么记」更重要；dreaming 负责纠错、建 wiki、把要点提到记忆层级顶端。

## 1. 先说结论

Anthropic 这篇文章的核心不是"给 agent 加一个向量库"，而是把**记忆当成一个会生长、会出错、需要整理的系统**：

- **记忆是知识，不是上下文**：agent memory 指 Claude 从经验中学到、能跨会话保留的知识；权重更新、单次对话里的 in-context learning、压缩对话都**不算**。
- **记忆是对未来的预测**：写一条规则，就是在赌"以后还会用到"。
- **判断"什么值得记"比"怎么记"更重要**：给强模型固定规则反而会削弱记忆带来的收益。
- **"做梦"（dreaming）是整理记忆的方式**：在空闲时回看日志和对话记录，纠正错误、建 wiki、把要点提到记忆层级顶端。

## 2. 人的记忆给了什么启发

作者先讲了一个类比。人类的**海马体**（hippocampus）在当下快速捕捉经历，但只有一部分经历会被**巩固**（consolidate）成长期知识。很多巩固发生在我们"离线"的时候：睡觉、安静休息时，海马体会**重放**（replay）最近的经历，逐步把它们整合进**新皮层**（neocortex）。

agent 也可以这样分工：agent 把工作记在日志、transcript 里；**研究者（Letta、UC Berkeley）提出过 "sleep-time compute"**——让模型在交互之间的空闲时间重新组织已有上下文。同样的思路可以用来整理记忆：回看日志、修正错误、产出新的笔记和表示。Anthropic 把这个过程叫 **dreaming（做梦）**。

## 3. 什么才算 agent memory

定义很关键，因为它划清了边界：

> **agent memory = Claude 从经验中获得、并在会话之间保留下来、以可读上下文形式存下来的知识。**

明确**排除**的三类：

| 不算 | 为什么 |
| --- | --- |
| 权重变化（训练时的参数） | 那是模型能力，不是运行时记忆 |
| in-context learning（单次对话里学到的） | 会话结束就没了 |
| compaction（压缩旧对话以腾出窗口） | 那是腾地方，不是积累知识 |

这个定义决定了后面所有实验都在测同一件事：**换一个会话，它还记不记得、用不用得上。**

## 4. 记忆笔记：先把「重要的事」记下来

人脑里，经历前后释放的化学信号会给记忆**打标记**，被标记的记忆在离线时更容易被重放。对应到 agent：Claude 可以在会话进行中把**显著事件**打上标记，或者直接写进记忆存储（比如一个装着笔记的文件夹）。

但这里有个真问题：**Claude 怎么在当时就知道什么是"显著"的？它还看不到后面会发生什么。**

## 5. 记忆是对未来的一次预测

作者的说法很直接：**记忆有时候就是一种预测**。

- 写下一个"已验证的事实"，是在预测"未来的会话会想直接信这条，而不再去核对"。
- 写下一个"规则"，是在预测"这个模式还会再出现"。

随着模型变强，Claude 做这种预测的能力也变好了——这也是后面 CL-Bench 实验想量化的东西。

## 6. CL-Bench：模型怎么学会「学习循环」

**CL-Bench 1.0** 是一个测"agent 能否用记忆处理长程任务"的基准。文中用的任务：让 Claude 反复查数据库答题，答完后告诉它正确答案，它可以写一条记忆帮以后答题。

实验用 **Claude Managed Agents**，每道题开一个**全新会话**，唯一例外是：它能访问一个跨会话保留的**记忆目录**。

不同模型长出了不同的"学习循环"：

| 模型 | 记忆行为的差别 |
| --- | --- |
| Sonnet 4.6 | 记忆目录里散着一堆文件，每条都是**没验证过的猜测** |
| Opus 4.7 | 把笔记收敛成**一份参考文档**，开始标记"已验证 / 未确认" |
| Sonnet 5 | 评分确认后把答案标成 confirmed；答错就写一条**更正** |
| **Opus 5** | **第一个真正闭环**：条目里有规则、有"我怎么知道这规则是真的"、有之前题目的答案、还有自己踩过的坑的警告 |

Opus 5.5 和 Sonnet 5.5 也闭环了，用记忆沉淀"已验证的答题规则"。有记忆时两者得分和 Opus 5 差不多——**但它们无记忆时的基线本来就略高**。

## 7. Pokémon：Claude 学会判断「什么值得记」

第二个实验是玩 **Pokémon Red**——一个长程、状态不断变化的任务，用来测 Claude 对"该往记忆里存什么"的判断。

每个模型开局给一个记忆文件夹，可以边玩边读写。作者对比了 **Sonnet 3.7** 和 **Fable 5** 各自跑到约 10,000 步时的记忆文件夹：

| | Sonnet 3.7 | Fable 5 |
| --- | --- | --- |
| 写了多少 | **413 个文件 / 225 个文件夹** | **9 个文件 / 2 个文件夹** + 一个 `global.md` |
| 得到徽章 | 1 枚 | **4 枚** |

问题出在哪？**Pokémon 的游戏状态一直在变**，Sonnet 3.7 那种细致的记录**持续过期**。于是它越玩越要把时间花在翻记忆上，而不是玩游戏。文中举了个具体的：大约 10,000 步时它开始整理第 4 个 "master" 文件夹，接下来 17 步里建了 6 个文件、删了 9 个，**游戏里一步没动**。

Fable 5 的判断标准不同：**只记游戏不会直接告诉你的东西**。

- 像"有多少钱""在地图哪个位置"——每回合都能从屏幕上读到，存下来是冗余。
- 策略、计划、验证过的规则——不写下来就消失。

它的 `global.md` 相当于一个**仪表盘**：当前目标、预先写好的打道馆计划、以及它自己用记忆的规则；`locations/` 放路线导航，`gameplay/` 放对游戏机制的策略。举个原文里的例子：连续 7 个精灵球没抓到 Magikarp 后，它写下"如果连续 3+ 个球失败，就**改变节奏**（在菜单步骤间插入额外的 wait）——这次就是在改动之后抓到的"。

Opus 5.5 用了类似做法：只维护一个小文件夹，记当前目标和下一步，边玩边重写，最后**通关了游戏**。

## 8. 该告诉它「为什么记」，而不是「怎么记」

Anthropic 的经验是：**说清记忆是干什么用的，但别规定它怎么用。**

- CL-Bench 上只是告诉 Claude "有一个记忆文件夹可用"，就足够 Opus 4.7 和 Opus 5 有效使用，并带来明显提升。
- 反过来，他们测了"每条规则单独给一条"的强约束。结果是：规则设成"**只记录失败**"时，**Opus 5 和 Opus 4.7 都失去了记忆带来的大部分提升**。对强模型来说，**让它自己判断显著性，比预先给固定规则更有效**，固定规则甚至会削弱表现。
- **引导对老模型帮助最大**：Sonnet 4.6 经常根本不读记忆文件、也不去验证自己的猜测；提示它"答题前先读记忆、并显式验证假设"后，它的基准分**几乎翻倍**。Sonnet 5 不用提示，答题前读记忆的比例是 **9/10**，Sonnet 4.6 不到一半。

对前沿模型，他们通常只给简单指引：**用户要求时、或明显值得记时，就写记忆笔记，剩下的判断交给 Claude。**

## 9. 做梦能纠正记忆

记忆是会在当时写错的，也会随环境变化而**漂移**。做梦给 Claude 一个机会：**拿笔记去和原始 transcript 对照，验证它**。

原文的例子是 Pokémon 的月见山（Mt. Moon）：入口在西、出口在东，入口附近有个陷阱——一段**单向台阶**，踩下去就掉回你来时的路，而且爬不上去。Claude 把宝可梦中心（PokéCenter）当路标，所以"走不走下台阶"取决于它认为中心在山哪一侧。

有一次它写错了：**中心在东侧**。结果走出中心就宣布"Mt. Moon 在我身后了"，把笔记更新成"Mt. Moon DONE"——其实并没有。几步之后它走下台阶，掉回原路；导航工具没显示落差，它还得出了"我跑太偏西了"的错误结论。

**用做梦跑一遍**：Claude 把这条笔记和会话 transcript 对照，发现错误并重写。有了正确笔记，它直接回到月见山，最终到达 Cerulean City。而用未纠正笔记的那一局：掉回去 **3 次**，第 3 次后它写"我要停下来，不再循环了"；自动回复让它继续，它一路退回山前的 Pewter City，**始终没到 Cerulean**。

## 10. 做梦能建记忆表示（wiki）

做梦还能让 Claude 造出**帮它导航记忆的表示**，最典型的是 **wiki**：一组由 Claude 自己写、自己维护的页面，把某个主题的知识收在一起，并**链接到其他笔记**。这些链接相当于一张地图，需要时能快速定位。

作者用一个真实语料测了 wiki 的价值：Anthropic 在 5 月收购的公司 **Stainless** 的内部文档，约 **350,000 个文件、约 420M tokens**。他们出了 **25 道题**，给 Claude 一个搜索工具，同时让它用做梦**先把这个语料建成 wiki**。

**128 个会话**里，Opus 5 agent 反复探索文件、写/修 wiki 页、合并重复、对照来源核验。会话之间靠共享日志协调、每轮在前一轮基础上继续。结果：

- 做梦从 **2 个会话**扩到 **128 个会话**，25 道题的得分从 **13% → 48%**（按评分标准计）。
- wiki 是**增量**长出来的：早期像新员工，只能答有限的问题；dream 得越多，知识地图越丰富，像老员工。
- **wiki + 搜索**一起用，总分随 wiki 增长从 **54% → 61%**；只用搜索是 **53%**，只用 wiki 最高 **48%**。
- 用上搜索 + wiki，每题还**省了约 20,000 tokens**。

不是所有任务都吃 wiki。用 **Harvey LAB** 基准 + 一个并购文档集测时：

- 24 道并购题（**一半以上需要跨多份文档**整合）：用 wiki 得 **87%**，只用搜索 **73%**。
- 另一个 LAB 任务，评分点大多能从**单份文档**里搜到：wiki **没有明显增益**。
- 还有一个任务里，**wiki 长得比原始文档还大**——作者拿博尔赫斯的《论科学的精确性》打比方：地图画得和帝国一样大，等于什么都没抽象。

## 11. 把笔记提到记忆层级顶端

做梦还能把某些笔记**提升到记忆层级的顶层**，由 agent 框架在**每个会话开始时预加载**进上下文。这样 Claude 不用搜，甚至不用知道"有东西可搜"。

但这一步要小心：

- 注入的记忆**要占 token**；
- 一条错笔记会被**带进每一个会话**；
- 加载进来**不等于会遵守**——Claude Code 的文档就提醒，指令文件越长，遵守度越低。

所以顶层必须**保持很小**，做梦在这里的主要工作就是**压住规模**：把细节往下层挪，只留链接。Claude Code 的 auto memory 就是这么做的：每个会话**只加载 `MEMORY.md` 的前 200 行或 25 KB**，这个头部充当索引，告诉 Claude "它知道什么、去哪找"。

## 12. 让记忆围绕目标生长

做梦还能**塑形**记忆的生长方向。像 **Claude Duet** 这种助手，记忆围绕"它服务的那个人"来组织更合适，dreaming 可以按目标来调。

原文举了 LAB 里的并购任务：给一批合同，法律简报的评分点是"是否准确描述合同条款"。

- 一开始只给建 wiki 的基础指令，**没告诉它条款有多重要**。建 wiki 时**多个 agent 同时往一张共享的合同条款表里写**，互相覆盖，结果 57 条事实只剩 **41 条（72%）**。
- 后来改成：**每份合同一个 agent、各自一页，逐字引用条款**而不是汇总到共享表。结果 **57/57 条事实**都留下，简报 **100%** 达成评分点。
- 更好的指令是**跑循环找到的**：Claude 复盘失败 → 提出修改指令 → 重建 wiki，自己发现"必须逐字跟条款"。

## 13. 做梦能补上单次会话的缺口

Claude 写记忆笔记时，只看得见**当时那个会话**的上下文。做梦可以**跨多个会话**找共同模式、纠正常见错误。

比如建 wiki 时，Claude 有时会链接到**还没创建的页面**。第二次 dreaming 就补上了这些洞：某个任务里，它找到 **9 个指向缺失页面的链接**，把它们改指到同一份文档的已存在页面，还新增了 3 个页面（含一个索引）。

## 14. 还没解决的问题

作者列了几个开放问题，没有给答案：

- **什么时候该写记忆？** 在任务进行中写，能捕捉当下的显著性、立刻可用，但会**分散注意力**；放到 dreaming 里写，不占当前注意力，但产出**不一定马上可用**。
- **怎么保持记忆不过期？** 模型会写错、环境会变、记忆会漂移。dreaming 能修，但要**花算力**；让它持续核对**所有**记忆不现实，更实际的是**聚焦在容易变的信息**上，或按"记忆被访问的频率"调 dreaming 的节奏。
- **transcript 搜索算不算记忆的地基？** 表示（wiki）+ 搜索有时有效，但维护表示要花算力，还得防错误和幻觉。
- **没有模型真的知道未来会发生什么**——所以 dreaming 的价值是：**回头看**，用算力整理记忆、纠错、维护表示，让未来的会话更容易取用。
