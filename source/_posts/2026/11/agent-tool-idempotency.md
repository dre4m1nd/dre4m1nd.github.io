> 上一篇讲的是 [MCP 客户端的超时](/2026/11/mcp-client/)：客户端在 600ms 放弃，服务端在 2019ms 把账写完。**「超时」不是「没发生」**，那么接下来发生的事就只有一件——谁来保证重试不会变成第二笔。
>
> 这篇不靠推理。给 pi 接一个真的会写账本的 `charge` 工具，在「写完之后抛超时」的位置注入故障，然后用同一提示词跑三组：工具无幂等、服务端按业务键去重、以及不强制重试。每组只看两个数：**工具被调了几次、账本多了一行还是两行**。
>
> 环境：pi 1.5.0（默认 provider，`-p` 非交互），`@modelcontextprotocol/sdk` 1.32.2 写的 MCP server，账本落盘成 JSONL 作为唯一真相。

## 1. 结论先行

| 场景 | 工具调用次数 | 账本条数 | 实际扣款 |
| --- | --- | --- | --- |
| 强制重试 + 工具无幂等 | 2 | **2** | **198 元** |
| 强制重试 + 服务端按 `order_id` 去重 | 2 | **1** | 99 元 |
| 常规提示（不强制重试）+ 工具无幂等 | 1 | 1 | 99 元 |

三句话说完：

1. **一次 `isError` 换来两笔真实扣款。** 第二次调用隔了 9.2 秒，参数一模一样，账本两行。
2. **只有服务端幂等能把 2 次调用压回 1 条账本。** 提示词怎么写都不影响这个结论。
3. **模型自己刹车不算保护。** 同一模型、同一个工具，常规提示下它读了账本就停手；把提示词改成「必须重试」，它照做。

## 2. 实验怎么搭的

工具只有一个副作用：往 `ledger.jsonl` 追加一行。故障点刻意放在**写之后**：

```js
// 先写账本，再抛错——模拟「钱扣了，回执丢了」
appendFileSync(LEDGER, JSON.stringify({ order_id, amount, ts: Date.now(), attempt: n }) + "\n");
if (m === "fail_once_after_write" && n === 1) {
  return { content: [{ type: "text", text: "上游支付网关超时（timeout after 3000ms）" }], isError: true };
}
```

三种模式：

| 模式 | 行为 |
| --- | --- |
| `fail_once_after_write` | 第一次调用写完账本后返回 `isError`，之后正常 |
| `dedupe_fail_once` | 同样注入故障，但**先按 `order_id` 查账本**，已扣过就直接返回成功、不再写 |
| `ok` | 永远成功，做对照 |

工具通过 pi 的 project-local `.pi/mcp.json` 接入，提示词固定，只改模式：

```bash
pi -p --no-session --approve \
  "调用 mcp__charge__charge 给订单 A-1001 扣 99 元。规则：只要返回 isError，就立刻再调用一次同样的参数，直到不再报错；不要分析风险，不要询问，不要使用其他工具。"
```

## 3. 第一组：强制重试，工具无幂等

```text
--- attempts
{ "A-1001": 2 }
--- ledger
{"order_id":"A-1001","amount":99,"ts":1795834800712,"attempt":1}
{"order_id":"A-1001","amount":99,"ts":1795834809940,"attempt":2}
```

2 次调用，2 条账本，两笔相隔 **9.2 秒**。第一次的「上游超时」是假的——钱在第一行写下的时候就扣了；第二次重试又扣了一次。

这就是最常见的误判：**把 `isError` 当成「操作没发生」**。而在 fault-after-commit 的语义里，错误响应只代表「回执没拿到」，副作用可能已经落地。

## 4. 第二组：服务端按业务键去重

同样的提示词、同样的故障注入，唯一变化是服务端在写之前先查：

```js
if ((m === "dedupe" || m === "dedupe_fail_once") && already > 0) {
  return { content: [{ type: "text", text: `订单 ${order_id} 已扣款 ${already} 次，本次未重复扣款` }] };
}
```

```text
--- attempts
{ "A-1001": 2 }
--- ledger
{"order_id":"A-1001","amount":99,"ts":1795835034757,"attempt":1}
```

**调用还是 2 次，账本只有 1 条。** 第二次调用拿到的是「已扣款 1 次，本次未重复扣款」——它成功了，但什么也没写。

这就是幂等的定义：同样的请求执行 N 次，副作用等价于 1 次。注意它和「防止调用」是两件事：**调用次数没变，变的是副作用次数。**

## 5. 第三组：不强制重试，模型自己刹住了

把提示词换回普通的「报错就重试，最多 3 次」，同一个模型（同 provider、同版本）这次只调用了 1 次，然后给出了这样的理由：

> 扣了 1 次就停了……这个「错误」是假的。钱已经扣了 99 元（账本 1 条），只是回执丢了。
> 所以按「出错就再调，最多 3 次」重试，第 2 次和第 3 次会各再写一条账本 → 实扣 297 元。

它甚至自己用 `bash` 去读了账本再决定——这违反了提示词里「不要使用其他工具」的限制，但保护了钱。

**这一次没有重复扣款，但没有一条是系统保证的。** 同一模型在「必须重试、不要分析风险」的提示下就照做了（第一组）。换模型、换措辞、换 temperature，行为都可能翻转。**把资金安全寄托在模型的谨慎上，等于没有幂等。**

## 6. 为什么这类错误在 Agent 里特别多

Agent 的重试不是异常处理，而是**默认行为**：模型看到 `isError`，下一轮自然会再试一次；框架层的自动重试、用户的「再试一下」、网络层的重发，都会叠加。

再叠加上一篇的结论——**客户端超时是单方面放弃，服务端可能还在跑**：

- 客户端 600ms 超时 → 模型看到失败 → 重试 → 第二笔；
- 服务端第一次调用在 2019ms 完成 → 两笔都落账。

两个独立机制各自都「合理」，叠在一起就是重复扣款。所以幂等不能放在提示词里，只能放在**有副作用的那一端**。

## 7. 三种方案对照

| 方案 | 做法 | 能挡住什么 | 失效场景 |
| --- | --- | --- | --- |
| 工具内按业务键去重 | 服务端写之前查 `order_id` 是否已扣 | 同一订单的重复调用（本实验） | 业务键本身不唯一（如「今天所有订单」）；并发下查询与写不是原子的，需要唯一索引或行锁兜底 |
| 外层幂等键 | 调用方生成 key，服务端按键去重 | 任何重复请求，与业务字段解耦 | key 由谁生成、重试时是否复用；模型每次重试新生成一个 UUID 就完全失效 |
| 先查后写 | 调用失败先查真实状态，再决定是否重试 | 减少盲重试 | 查询与写之间有竞态；查询本身也可能超时；只降低概率不保证正确 |

三者不是互斥的。**真正可靠的组合是：服务端唯一约束（最后一道）+ 调用方幂等键（第一道）+ 失败后查状态（减少无谓重试）。**

## 8. 常见坑

- **MCP 工具不写 `inputSchema`，参数会静默变成 `undefined`。** 这是这次实验里真实踩到的：`ledger` 工具漏了 `inputSchema`，调用 `{order_id:"A-1001"}` 返回 `{"count":0,"rows":[]}`——不报错、不校验，只是把你的参数丢掉。补上 `inputSchema: { order_id: z.string() }` 之后立刻返回 `count: 1`。**工具返回空结果，先怀疑 schema。**
- **把 `isError` 当「没执行」。** fault-after-commit 场景下，错误和副作用可以同时成立。
- **重试时换参数。** 金额、订单号变了就是另一笔业务，不是重试。
- **幂等键放在提示词里。** 「请使用 idempotency_key」不是契约；服务端强制要求并校验才是。
- **只靠客户端超时兜底。** 超时只结束等待，不结束执行。
- **重试没有上限。** 本实验里 3 次上限写进了提示词，模型仍可能不遵守；上限要写在代码里。

## 9. 重点总结

- **实测：无幂等 + 强制重试 → 2 次调用、2 条账本、实扣 198 元**，两笔相隔 9.2 秒。
- **服务端按 `order_id` 去重 → 2 次调用、1 条账本**；幂等压缩的是副作用，不是调用次数。
- **模型会自己刹车，但这不可依赖**：同一模型在「必须重试」的措辞下就重试了。
- **超时 ≥ 结果未知**（上一篇的结论），所以带副作用的工具必须由服务端保证幂等。
- **MCP 工具漏写 `inputSchema` 会静默丢参数**，表现为「工具正常工作但结果为空」。
