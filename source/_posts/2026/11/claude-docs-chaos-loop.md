> Claude Docs 是一个文档编辑器：你、同事和 Claude 可以同时在一个文档里读写、评论。服务上线是 2026 年 9 月 16 日。到 9 月 22 日，用户创建了超过 **460 万**个文档；**20 亿**次请求里只有 **60** 个服务端错误，**一次都没有回滚**。整个服务跑在约 **50** 个内存优化型 Pod 上。
>
> 作者 Vivek Nair 把成绩归功于两个决定：一个**按上线规模搭的混沌循环**，以及**让服务对 Claude 可读**。这篇是原文的提炼与转述。

## 1. 一、背景：单机验证撑不起上线

上线前三周，Claude Docs 还只是跑在单节点上的概念验证，只有 Anthropic 内部的几千人在用。团队自己的估算：上线头几天就会有几百万个文档。单机上的几千用户说明不了任何问题，而真实的上线流量又还拿不到。

于是 9 月 4 日——上线前约两周——他们让 Claude 去驱动一个**镜像生产环境的 staging 集群**（每天生成超过一百万份合成文档），并故意打坏核心组件，然后把循环**放着不管，让它一直跑**。

## 2. 二、混沌循环：一个跑两周的 Claude Code 会话

循环本身很简单：**选场景 → 跑压测 → 读遥测 → 提方案 → 改代码 → 部署到 staging → 再压测**。它就是一个留在 Claude Code 里持续运行的会话：主会话做协调器，把大部分活派给子代理——最忙的一周通常同时跑 11 个子代理，峰值 30 个。协调器还会通过 Slack MCP 联系 Anthropic 内部其他负责同类基础设施的团队，让他们的代理帮忙检查扩展方案里已经踩过的坑。

场景故意挑「被害妄想」级别的：

- 单日新建 1000 万份文档；
- 2.2 万个长连接同时重连；
- 一份热门文档几百人围观、服务器在加载文档时被杀、数据库卡死。

每轮迭代结构相同：压测工具把某个功能（比如文档创建）压到饱和，Claude 通过 Datadog MCP 读遥测，给出一个简短的选项菜单和推荐方案。如果方案容易回退，Claude 就自己写代码、部署到 staging、重跑测试。

有两条**必须人批**的红线：任何难以撤销的变更（改数据库 schema、改键布局、改文档的存储与物化方式）必须先停下来问人。Claude 通常带着推荐方案来问，作者基本都批准了——schema 变更就是典型：合理答案往往有好几个，中途换方向很痛苦。

整个测试过程还必须守住两条不变量：

1. 文档必须**几乎瞬间打开**（即使历史很长）；
2. 一旦服务器确认了某次编辑，测试必须证明这次编辑**还在**。

## 3. 三、让服务对 Claude「可读」

作者引用了同事 Felix Rieseberg 的观点：把提示的「高度」抬高——**要结果，而不是任务**。不是让 Claude 修一个个崩溃，而是让它把应用做到**不崩溃**。要做到这一点，代码必须让 Claude 能自己拉崩溃报告、跑复现压测、验证修复。

为此他们做了两件事：

### 3.1. 诊断循环：遥测随写随加

每轮迭代 Claude 都读遥测，并自己补上它认为缺失的指标——以前遥测是出了事才补，现在变成边写边加。

内存是最好的例子。压测早期，一个大的文档在 Pod 上占了约 **3 GB**。Claude 第一反应是缩小缓存、让服务器更早驱逐文档；下一轮压测发现内存其实在**某个依赖内部的另一个缓存**里，于是撤回了改动。它用更细的内存分析继续缩小范围，最后定位到：**每一次按键都把文档复制进好几个不同的数据结构**，每次增加几 MB。Claude 把这些结构改成 copy-on-write，让它们共享同一个引用。迭代约三天后，那份文档的内存峰值降到约 **180 MB**，上线所需的内存优化 Pod 预估从 **500 多个降到约 50 个**。

### 3.2. 选「可解释」的技术栈

他们挑运行时和依赖的原则是：**任何被测量出来的数字，都能追溯到我们自己写的代码**。

- **用 Rust**：没有 GC，文档的内存都待在框架自己定义的结构里。内存涨了，Claude 能指着具体那个结构，改掉它，下一轮看内存是否下降。作者也提到：Anthropic 内部 Go 工具链很好，两种语言没有做过比拼，这是他们在 Rust 上的经验。
- **依赖降到最低**：每个库都带来别人写的、难以核算的数据结构；少数必需的库直接 vendor 进来，自己读、自己量。

文章特别强调：**避开 GC 是「下注」而不是「实验」**——他们预期 GC 会让内存和延迟按回收器的节奏波动，给信号带来噪声。Rust 对人来说不好写，但 Claude 写得很好，所以这个缺点现在不那么重要了。

## 4. 四、上线周：629 次发布，零回滚

服务扛住了上线规模：第一个 100 万文档在约 30 小时内出现，到 9 月 22 日超过 460 万。9 月一共发布 **629** 次，**没有一次回滚**。

发布周「怪异地熟悉」：Claude 很擅长想象服务会怎么挂，预演过的场景里，**10 个有 7 个真的在生产发生了**——而 staging 上早已跑过，Claude 把修复都放在运行时开关后面；基础设施一有压力，通常翻个开关就行。

## 5. 五、为什么现在才行

几个月前这件事大概做不成。老模型读遥测没问题，但长循环跑到一二十轮就开始「忘记在优化什么」，作者不得不反复重申目标——其他同事称之为 **goal drift（目标漂移）**。新的前沿模型是为长任务设计的：在多次上下文压缩（compaction）之后，Claude 仍守住了全部不变量，作者一次都没有重复过。

作者也提到这不是独一份：Vercel 用类似的「有监督的代理循环」把 Turborepo 提速了 **96%**。

## 6. 六、成本：约 12.5 万美元推理

按 Claude Fable 5.2 的 API 标价（2026 年 11 月），从 8 月底到上线日，作者大约用了 **12.5 万美元**的推理。放在两年前，这种规模的工作他估计需要一支工程师团队做**约六个月**。

两点说明：

- **上线规模特别大**：相当一部分钱花在只有这个规模才需要的基础设施上，而这些基础设施本身还需要更多推理来理解；
- **摸索流程也烧了不少 token**：循环在调试搭法期间一直跑着；以现在的认知，他认为可以只花**一半左右**。

对更小的服务，文章给了一个粗略估算：经典小团队栈（两台凑合的 K8s 节点 + 一个 Postgres），把只服务内部/产品/多 Pod/精细限流的部分去掉后，只剩约三分之一改动；按这个规模折算，两周的推演大约 **3000–10000 美元**（未经实际运行验证）。

## 7. 七、想自己试的五个步骤

前提：一名工程师 + Claude Code + staging 环境 + 一个可观测性平台。

1. **给 Claude 遥测权限**：多数可观测性平台都有 MCP server。
2. **让 Claude 写压测脚本**：对 staging 抛出真实流量的 10 倍，并故意打坏——杀实例、卡数据库、在流量高峰里发布，都是好的起点；然后让 Claude 不断修复倒下的部分。
3. **技术栈向「可测量」倾斜**：对他们来说是 Rust + 尽量少的依赖。
4. **开跑前写下最重要的技术不变量**，交给 Claude。
5. **难以撤销的操作**：让 Claude 停下来，给出几个选项和明确推荐。

## 8. 重点总结

- **混沌循环**：把「压测 → 读遥测 → 提方案 → 改代码 → 再压测」做成持续运行的闭环，主会话协调、子代理干活；难撤销的变更人批。
- **服务可读性**：遥测随写随加、用 Rust 避开 GC、砍依赖并 vendor——让每个数字都能追溯到自己的代码。
- **结果**：20 亿请求 60 个错误、零回滚、629 次发布；Pod 预估从 500+ 降到约 50。
- **前提**：新模型能长时间守住目标（不漂移）；成本约 12.5 万美元，小团队折算约 3000–10000 美元。
- **心法**：抬高提示的高度——要「不崩溃的结果」，并搭好让模型自己复现、验证的脚手架。
