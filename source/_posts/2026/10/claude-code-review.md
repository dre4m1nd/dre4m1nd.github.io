## 

**代码审查的目的不是"找 bug"，而是"按风险匹配检查"——这个改动可能出什么问题，哪个自动/人工检查最该抓住它。** 当 90% 代码由 AI 写、每天几万次改动时，人工逐行审不动了，必须上 AI。但真正兜底的不是"AI 不漏"，而是**一套能快速下架和修复的机制**。个人开发者能搬走的是：让 AI 先自证、按风险决定看多细、保证出问题能秒级回滚。

## 一、代码审查到底在审什么

很多人把 code review 等同于"找 bug"。但《How the Claude Code team does code review》给了一个更准确的定义——审查有两个职责：

1. **上线前发现并修复问题**
2. **让团队共享对代码库的理解**

判断标准，不该是"有没有人逐行读过"，而应该是：

> 这个改动可能出什么问题？哪个检查（自动还是人工）最适合抓住它？

这句话把"审查的形式"换成了"风险的匹配"。文档改错一个字，和自动更新器改错一个分支，风险差了几个数量级，却常常被同一套"人肉逐行看"对待——这本身就是错配。

从风险维度看，审查真正要覆盖三类东西：

| 维度 | 要回答的问题 |
| --- | --- |
| 正确性 | 逻辑对不对、边界对不对、有没有引入回归 |
| 一致性/可维护性 | 符不符合项目约定、会不会给后人挖坑 |
| 风险控制 | 出错时影响面多大、能不能快速收住 |

第三类最容易被忽略，但它恰恰是后面所有讨论的落脚点。

## 二、为什么人工审查越来越审不动

先看几组数字（来自 Claude Code 团队的真实数据）：

| 指标                         | 数字                         |
| -------------------------- | -------------------------- |
| Claude 写 Claude Code 的代码占比 | **~90%**                   |
| Anthropic monorepo 每天落地改动  | 5 月 ~2500 → 9 月 **30000+** |
| 合并 PR（6→9 月）               | **翻倍多**                    |
| 同期需要 revert 的比例            | **下降 40%+**                |

当每天有 3 万次改动落地，**"逐行读每一个 diff"在物理上就不可能了**。人工审查卡在三个地方：

1. **量**：改动的增长速度远超人能读的速度。
2. **注意力**：把资深工程师从深度工作里拽出来，去接一个例行错误，成本远高于自动审查。
3. **两头的账**：人的时间花在"审"和"修被坏代码搞坏的东西"两头。只砍第一头，第二头涨上来，等于没省。

所以审查的形态也变了：以前是"写完 → 开 PR → 等同事"这种**终点的一道门**；现在是**像拼写检查一样持续运行**——大多数改动在人来之前已经被 AI 审过、修过一遍。

这里有个容易忽略的成本结构：**衡量审查效率，不能只看审得多快，还要看 revert 率和事故率有没有涨。** 这两个才是护栏，涨了就说明时间只是被挪走了。

## 三、为什么必须上 AI 审查

不是"AI 更聪明"，而是**机器能读的量和稳定性，人已经比不了**：

- 每个 PR 都能在人来之前过一遍，不疲劳、不遗漏、可重复；
- 内部 PR 拿到实质性评论的比例从 **16% → 54%**；
- 大 PR（>1000 行）大多能揪出问题，小 PR 大多干净返回，**信噪比可控**。

但 AI 审查不是万能，它有三个典型毛病，必须正视：

1. **会漏**：再好的模型也可能放过真 bug；
2. **会误报**：为了抓 bug 疯狂 flag，人就会被噪声淹没；
3. **会自嗨**：一个 agent 作者 + 一个 agent 审查者，可以互相喂到天亮——原文里真有一个 CLI PR **一夜跑了 50 多轮**。

所以问题不是"要不要上 AI"，而是**怎么把 AI 审查做成一套规范、能收敛、漏了也有兜底的流程**。

## 四、如何把 AI 审查做成规范流程

Claude Code 团队的做法是一条**七层流水线**。这张图来自原文，把一次改动从作者机器到用户的过程完整画了出来：

![FIG A：一次改动的生命周期](/img/code-review-fig-a.jpg)

> 图 1：一次改动的完整生命周期（源自原文）。绿色 = 自动化，橙色菱形 = 按风险由人决定，循环箭头 = 出错后的恢复。

每一层职责明确：

1. **PR 之前先自验证**：给 Claude 一个**能跑**的东西（测试、构建、跟设计稿对比的截图），要求**展示输出**，而不是说"我完成了"。Boris Cherny 的说法：**让模型能验证自己的工作，大概是最重要的一件事**，能让结果好 2–3 倍。反复被 flag 的问题，修**源头**（skill、lint、`CLAUDE.md` / `REVIEW.md`），而不是修这一处。
2. **每个 PR 都跑 AI 审查**：多组 agent 并行找 bug → 另一组投票 → 票数够才发评论。只涉及风格/清理的直接丢。剩下的按严重度排，标 `Important` / `Nit` / `Pre-existing`——**PR 没引入的老问题不该算在作者头上**。
3. **安全审查能卡合并**：bug 审查或安全审查只要还有未关闭的 finding，就禁止合并。
4. **自动检查能卡合并**：lint、类型、各平台测试、构建；一个 PR 可能在有人看之前就跑几十项。
5. **人工批准按风险分级**（最值得抄的设计）：

| 风险 | 例子 | 需要几个真人 |
| --- | --- | --- |
| 低 | 文档、文案、纯内部功能、带 flag 的增量 | 自动审查 + 安全绿了就 **0 人** |
| 中 | 普通产品改动；缓存、自动更新、系统提示 | **1 人** |
| 高 | 最高风险代码 + 永远要两人的路径 | **2 人** |

- 分级由**变更**决定，不由作者决定；只有可信作者能走轻路径；agent 的批准永远不算真人；谁发起谁负责；批准只覆盖某个 commit。
6. **merge queue + flag + 灰度**：merge queue 对 main 重跑所有检查；新行为先对内部员工上 flag；公开发布先走 `latest` 再走 `stable`。
7. **快速发现、快速回滚**：这一层正是下一节的重点。

另外，**reviewer 自己也要进化**：把事故变成 eval（收集历史上导致事故的 PR，工程师确认 bug 在哪，reviewer 每天跑这套集合），测噪声，并强制审查收敛——3 轮后让作者退后重新考虑方案、头几轮后只审 diff、按类别修、不重复已发的 finding。

## 五、别怕 AI 漏，关键是能快速下架和修复

这一段是全文我最认同的观点：

> **不怕 AI 漏掉漏洞，怕的是没有一套能快速下架和修复的机制。**

AI 审查再强，也一定会有漏网的。所以最后一层不是"更严格的审查"，而是**让错误发生得可逆、可快速收住**。这条恢复链路是这样的：

几个要点：

- **flag 能一键关**：新行为都藏在 feature flag 后面，出问题不用发版、不用回滚代码，直接关掉；
- **灰度发布**：先内部 → 再 `latest` → 再 `stable`，让少数人先踩坑；
- **on-call + 事故复盘**：每周轮值，复盘时追问"哪一层本该抓住它"——把事故变成下一轮 eval 的样本；
- **快速回滚**：出问题先 revert，再慢慢查。

原文里有句很实在的话：**放慢当然能降低错误率，但那主要是因为你啥都做得少了。** 他们宁可练"更快发现和修复"，也不靠"审得更慢"。

所以真正的安全网是三层叠加：**AI 早发现 + 人工按风险把关 + 出错能秒级下架和回滚**。前两层降低出错概率，第三层降低出错的代价。只要第三层足够快，就不必因为"AI 可能漏"而不敢用 AI。

## 六、个人开发者能拿走什么

这套流程是大团队的，但里面的**思想**完全可以搬到个人项目：

1. **让 AI 先自证，别听它说"done"**：给它能跑的命令（测试、构建、lint），要求贴输出。这一步能挡掉大量低级错误。
2. **提交/合并前先自审一遍**：让 AI 做"找 bug / 简化 diff / 端到端验证"这三件事，人只看结论和证据，而不是从头读初稿。
3. **写一份自己的 `CLAUDE.md`**：把项目约定、目录结构、代码风格、"不要动哪些文件"写进去，让 AI 每次都读到。这是最便宜的"规范 AI"手段。
4. **小步提交 + 保证可回滚**：一个 commit 只做一件事；用 git 分支/标签让"撤掉"变成一条命令。个人项目没 flag，但"能快速回滚"这条原则一样成立。
5. **给自己的改动做风险分级**：文档、文案、样式改动可以大胆让 AI 改；涉及认证、加密、数据迁移、部署配置的，一定人工逐行看。
6. **别在 AI 自嗨时硬耗**：发现 AI 反复改同一个点、越改越多轮，就停下来重新想方案，而不是继续"再修一轮"。
7. **把踩过的坑记成清单**：每次出问题，问一句"哪一步本该拦住它"，把答案加到自己的检查清单或 `CLAUDE.md` 里——这就是个人版的"事故变 eval"。

一句话总结：**AI 审查负责把 90% 的例行错误挡在前面，人负责判断"该不该做、风险在哪"；而真正的底气，来自"出错了能马上收回来"的能力。**
